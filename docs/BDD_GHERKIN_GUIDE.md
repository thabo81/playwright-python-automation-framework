# BDD / Gherkin with Playwright

This guide documents the Cucumber-style BDD layer in the Python + Pytest + Playwright framework.

The project uses **pytest-bdd** to connect Gherkin feature files to Pytest fixtures and existing Playwright Page Objects. It complements ordinary Pytest UI/API tests; it does not replace them.

## Architecture

```text
Gherkin Feature
      ↓
Step Definitions
      ↓
Pytest Fixtures
      ↓
Page Objects
      ↓
Playwright
      ↓
Browser
```

## Dashboard Feature

The dashboard workflow lives in `features/dashboard.feature` and proves that BDD can reuse the framework's authenticated session and Page Object architecture beyond login.

It includes two scenarios:

- The dashboard title is displayed.
- The authenticated user sees the personalized welcome message `Welcome, Demo User`.

The feature's `Background` calls the `dashboard_page` fixture. That fixture wraps a Playwright page created through `authenticated_page`, which uses the saved storage state generated by the existing `authenticated_storage_state` fixture.

The dashboard steps live in `tests/bdd/step_defs/dashboard_steps.py` and are registered through `pytest_plugins` in `tests/bdd/test_dashboard_bdd.py`.

## Login Feature

The feature file is `features/login.feature`. It now uses two styles:

1. A standard `Scenario` verifies successful login.
2. A `Scenario Outline` runs the same negative-login behaviour against multiple example rows.

The Examples table currently supplies two negative cases:

| Example | Username | Password | Expected result |
|---|---|---|---|
| Invalid password | `testuser` | `WrongPassword` | Invalid username or password |
| Empty credentials | empty | empty | Username and password are required |

The empty cells deliberately pass empty strings to the login form. This is useful for checking required-field validation without creating a separate step definition just for this input.

## Step Definitions and Plugin Registration

The Python implementations live in `tests/bdd/step_defs/login_steps.py`.

The scenario module `tests/bdd/test_login_bdd.py` registers the separate step-definition module using Pytest's `pytest_plugins` setting:

```python
# Register the module so Pytest can discover its decorated step definitions.
pytest_plugins = ("tests.bdd.step_defs.login_steps",)
```

A normal Python import alone does not guarantee that a separate module's step functions are registered as Pytest fixtures. Registering the module as a plugin makes the step definitions discoverable by pytest-bdd.

## Scenario Outline and Examples

A `Scenario Outline` is a template. pytest-bdd executes the scenario once for each row in its `Examples` table.

The outline's placeholders (`<username>`, `<password>`, and `<expected_message>`) are substituted from the row before the matching step definitions execute.

The step uses `parsers.re(...)` with named groups and a non-greedy match. This allows the username and password values to be empty strings. The expected error step uses `parsers.parse(...)` to capture the expected message.

This is a small form of data-driven test design: the behaviour stays the same while the input data and expected result vary.

## Run the BDD Scenarios

Run only the BDD scenario module:

```bash
pytest tests/bdd/test_login_bdd.py -v
```

Run scenarios tagged as BDD:

```bash
pytest -m bdd -v
```

Run only the smoke scenario:

```bash
pytest -m "bdd and smoke" -v
```

Run the negative-login outline:

```bash
pytest -m "bdd and negative" -v
```

The feature-level `@bdd` tag and scenario-level `@smoke` / `@negative` tags support selective execution.

## Methods and Pytest-BDD Constructs Used

| Method / construct | Purpose |
|---|---|
| `@given(...)` | Maps a Gherkin Given step to a Python function. |
| `@when(...)` | Maps a Gherkin When step to a Python function. |
| `@then(...)` | Maps a Gherkin Then step to a Python function. |
| `parsers.parse(...)` | Extracts a value from a parameterized step sentence. |
| `parsers.re(...)` | Uses a regular expression and named groups to extract step arguments, including empty strings. |
| `Background` | Defines shared Given steps that run before each scenario in the feature. |
| `dashboard_page.navigate(...)` | Opens the dashboard using the authenticated Page Object fixture. |
| `dashboard_page.assert_loaded()` | Verifies that the dashboard title is displayed correctly. |
| `dashboard_page.assert_welcome_message(...)` | Verifies the personalized welcome message. |
| `pytest_plugins` | Registers a separate module as a Pytest plugin. |
| `scenarios(...)` | Generates Pytest test functions from scenarios in a feature file. |
| `login_page.open(...)` | Navigates through the existing LoginPage Page Object. |
| `login_page.login(...)` | Fills and submits the username and password fields. |
| `login_page.assert_login_error(...)` | Checks visibility and exact text of the login error. |
| `page.wait_for_url(...)` | Waits for the expected successful-login URL. |

## CI and Reporting

GitHub Actions runs the full Pytest suite, including BDD scenarios discovered under `tests/`. The workflow generates an Allure report and uploads the report and test evidence as artifacts even when tests fail.

The shared login Background and all three login BDD cases passed in GitHub Actions as part of a **10-test pass**. The new dashboard feature adds two more scenarios and will be considered verified when its workflow run passes. In the latest run, the full suite reported **10 passed in 3.43 seconds**. The workflow verifies tag filtering separately: `bdd and smoke` selected **1 passed, 2 deselected**, while `bdd and negative` selected **2 passed, 1 deselected**.

The Allure HTML report was generated and uploaded successfully. Inspection of the report confirmed three distinct BDD result entries: the successful-login scenario and both Scenario Outline examples. The results carry the expected `bdd`, `smoke`, and `negative` tags, allowing the feature behaviour and example-specific results to be reviewed in the report.

Allure result directories for the tag-filter checks are kept separate from the complete-suite results so the main HTML report continues to represent the full test run.
